# 브라우저 에이전트에게 맡길 때

로그인된 브라우저를 다루는 에이전트(예: Aside, Claude in Chrome 등)에게 구글 콘솔 작업을 맡기는 경우의 프롬프트 템플릿과 흔한 막힘이다. "예상" 막힘 표는 일반적으로 짐작되는 것이고, 실사용으로 확인된 것은 맨 아래 "관찰 기록" 표에 따로 적는다(확인됨 / 미확인을 구분).

## 프롬프트 템플릿

`<...>` 자리를 채워 쓴다. 비밀값은 어떤 경우에도 프롬프트에 직접 쓰지 않는다.

```
Google Cloud 콘솔(https://console.cloud.google.com)에서 현재 로그인된 구글 계정으로
웹 애플리케이션용 OAuth 클라이언트를 만들어 주세요.

[프로젝트]
- 기존에 다른 서비스가 쓰는 프로젝트, OAuth 클라이언트, 동의 화면은 수정하지도 재사용하지도 마세요.
  조회만 허용합니다. 기존 프로젝트에 승인된 URI를 추가하거나 동의 화면의 앱 이름/범위를 바꾸는 것도
  금지입니다(그 서비스의 로그인 화면에 영향이 갑니다).
- 이 앱 전용으로 새 프로젝트(이름: <프로젝트 이름>)를 만들고, 그 안에서 새 동의 화면과 새 클라이언트를 만드세요.
- 새 프로젝트를 만들 수 없는 제한(결제, 조직 정책 등)이 있으면 아무것도 바꾸지 말고 멈춰서 사유만 보고하세요.

[동의 화면]
- 앱 이름: <앱 이름>, 범위: <openid email profile 중 필요한 것만>
- 게시 상태가 "테스트"이면 테스트 사용자에 현재 로그인한 계정만 추가하세요.
  다른 사람의 계정을 추측하거나 임의로 추가하지 마세요.

[클라이언트]
- 유형: 웹 애플리케이션, 이름: <클라이언트 이름>
- 승인된 JavaScript 원본: <https://app.example.com>
- 승인된 리디렉션 URI: 정확히 아래 한 줄만 등록
  <https://app.example.com/auth/google_oauth2/callback>

[결과 기록 - 매우 중요]
- 클라이언트 ID와 Secret을 화면 출력, 터미널 출력, 채팅 응답에 절대 쓰지 마세요.
- 아래 파일의 해당 키 줄에만 값을 쓰세요. 다른 줄과 주석은 그대로 둡니다.
  파일: <~/path/to/.env.local> (git 이 무시하는 파일)
  키: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, ADMIN_EMAILS
- 끝나면 값 자체는 쓰지 말고 다음만 보고하세요: 키가 채워졌는지(예/아니오),
  리디렉션 URI가 정확히 등록됐는지(예/아니오), 어떤 프로젝트를 썼는지.
- 비밀번호나 2단계 인증이 필요한 단계에서 막히면 멈추고 그 사실만 보고하세요.
```

## 에이전트에게 맡길 때의 규칙

1. 에이전트 출력을 `head`, `tail` 같은 파이프로 자르지 않는다. 터미널 쪽 프로세스가 먼저 끝나 "종료됐다"고 오해하기 쉽다. 파일로 리디렉션하거나 백그라운드로 실행하고, 에이전트 자체의 세션 상태를 따로 확인한다.
2. 진행 상태는 에이전트 도구의 세션 목록으로 확인한다(Aside CLI 의 경우 `aside session list`). 세션이 기본적으로 임시(ephemeral)라 앱의 채팅 목록에 보이지 않는 도구도 있다. 보이지 않는다고 "지시가 안 됐다"고 단정하지 말고 세션 목록부터 본다.
3. 방향을 바꿔야 하면 새 세션을 만들지 말고 실행 중인 세션에 추가 지시(steer)를 보낸다.
4. 비밀 파일에 쓰는 마지막 단계는 `scripts/write_secrets.sh` 형태(출력 없음, 권한 600)를 쓰도록 안내하는 편이 안전하다. 에이전트가 직접 편집하게 하면 다른 줄을 건드릴 위험이 있다.
5. 작업 후 사람이 확인한다: 콘솔에서 등록된 URI 목록, 사용한 프로젝트, 비밀 파일의 키 채움 여부(값 비공개).

## Aside CLI 로 맡길 때 (1회 관찰)

Aside 는 로그인된 브라우저를 다루는 에이전트이고, `aside` CLI 로 터미널에서 작업을 맡길 수 있다. 아래는 직접 관찰한 사용법이다. 옵션과 동작은 버전에 따라 다를 수 있으니 `aside --help`, `aside guide` 를 먼저 본다.

```bash
aside "<프롬프트>"                         # 별도 세션을 만들어 실행 (기본 Guard 권한)
aside session list                         # 상태: running / idle / interrupted
aside session steer <id> "<추가 지시>"     # 실행 중 방향 수정
aside session stop <id>                    # 중지
aside settings save-sessions true          # 세션을 앱 채팅 목록에 남김
```

관찰한 점:
- `aside "<프롬프트>" | head -c N` 처럼 출력을 자르면 터미널 쪽 프로세스만 끝나고 세션은 계속 `running` 이다. 이를 "종료됐다"로 오판했다. 출력은 파일로 리디렉션하거나 백그라운드로 돌린다.
- 세션은 기본적으로 임시(ephemeral)라 앱의 채팅 목록에 보이지 않는다. 그래서 "지시가 안 됐다"고 오해하기 쉽다. `aside session list` 로 먼저 확인한다.
- 진행 내용은 CLI 로 볼 수 없었다. 볼 수 있는 것은 세션 상태와, 결과 파일의 변화(수정 시각, `scripts/check_secrets_file.sh` 의 지문)뿐이다. 세션 안의 세부 단계는 앱 화면에서 사람이 본다.
- 전체 작업 시간은 대략 15분 안팎이었다(1회 관찰).
- 같은 도구로 **읽기 전용 감사**도 시킬 수 있었다(프로젝트 목록, 동의 화면 상태, 클라이언트 설정 조회, 다른 프로젝트 비변경 확인). 모든 프로젝트를 순회하게 했더니 약 20분이 걸렸다. **감사 범위를 좁히는 것이 좋다**: 새로 만든 프로젝트 한 개의 설정 조회와, 필요한 경우 영향받을 수 있는 한두 개 프로젝트의 감사 로그 조회만 시킨다.
- 에이전트가 `새 프로젝트 만들기` 화면을 열어 할당량 경고만 읽고 취소한 경우가 있었다. 읽기 전용 감사 프롬프트에도 "생성/저장/삭제 버튼은 누르지 않는다"고 명시한다.

## 흔한 막힘 (예상 + 일부 관찰됨)

| 막힘 | 대응 |
|---|---|
| 구글 비밀번호 / 2단계 인증 요구 | 에이전트는 멈추고 보고. 사람이 직접 인증한 뒤 이어서 진행 |
| 여러 구글 계정이 로그인되어 있어 엉뚱한 계정 선택 | 프롬프트에 계정 이메일을 명시하고, 작업 전 현재 계정을 확인하게 한다 (이메일을 파일이나 채팅에 남기는 것이 곤란하면 계정 표시 이름으로 지정) |
| 콘솔 UI 개편으로 메뉴 이름이 다름 | 에이전트에게 메뉴 이름이 아니라 "동의 화면 구성", "OAuth 클라이언트 만들기"처럼 목적으로 지시한다 |
| 에이전트가 같은 계정의 다른 서비스용 프로젝트/클라이언트를 발견해 재사용하거나 수정하려 함 | **관찰됨(1회).** 사람이 세션 화면에서 알아채고 `steer` 로 "기존 프로젝트는 조회만, 새 프로젝트를 만들어 쓰기"를 지시했다. 이후 새 프로젝트가 실제로 만들어졌고(생성 시각이 지시 직후, 활동 로그의 프로젝트 생성 기록) 다른 프로젝트의 클라이언트 감사 로그는 오늘 결과 0개였다. 프롬프트 템플릿에 처음부터 금지 문구를 넣는다 |
| 새 프로젝트 생성 한도 또는 조직 정책 | 변경 없이 멈추고 사유 보고. 사람이 한도/정책을 해결 |
| 결제 계정 연결 요구 | OAuth 클라이언트 자체는 보통 비용이 없지만 프로젝트 생성에 요구될 수 있다(확인 필요). 멈추고 보고 |
| 동의 화면이 "테스트"인데 계정이 거부됨 | 테스트 사용자 추가 누락. 현재 계정 추가 |
| 입력란에 복사한 URI 끝에 개행/공백이 섞임 | 등록 후 `check_redirect_uri.sh --lint-only` 와 콘솔 표시값을 눈으로 대조 |
| 저장했는데 바로 `redirect_uri_mismatch` | 반영 지연 가능. 몇 분 뒤 재시도 |

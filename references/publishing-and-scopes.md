# 게시 상태와 범위

일부는 콘솔 화면에서 직접 본 것(`확인됨(1회)`)이고 나머지는 일반 지식이다. 한도와 정책은 바뀔 수 있으므로 공식 문서로 재확인을 권장한다. 화면 기록은 `console-ui.md` 를 본다.

## 게시 상태

| 상태 | 로그인 가능한 사람 | 비고 |
|---|---|---|
| 테스트(Testing) | 테스트 사용자로 등록된 계정만 | 테스트 사용자 한도 100명, 앱의 전체 수명 주기 기준 (화면 문구 확인됨, 1회). 영문 도움말에 `Authorizations by a test user will expire seven days from the time of consent. If your OAuth client requests an offline access type and receives a refresh token, that token will also expire.` 라고 적혀 있다(문서 기준, 직접 겪지는 않음) |
| 프로덕션(In production) | 구글 계정이 있는 누구나 | 민감/제한 범위를 쓰면 앱 검증이 필요. 로그인 기본 범위만 쓰면 검증 없이 게시 가능한 것으로 알려짐 |
| 내부(Internal) | 같은 Workspace 조직의 계정만 | 조직이 없는 개인 계정에서는 `내부로 설정` 이 비활성이었다(확인됨, 1회) |

관리자 2~3명만 쓰는 도구라면, 테스트 상태 + 테스트 사용자 등록이 가장 단순하고 안전하다. 단, 앱 쪽에도 별도의 허용 목록(환경변수 등)을 두어 이중으로 막는 것을 권장한다. 구글 로그인 성공은 "구글 계정이 있다"는 뜻이지 "우리 앱 사용 권한이 있다"는 뜻이 아니다.

## 범위(scope)

| 범위 | 분류(알려진 바) | 로그인 용도 |
|---|---|---|
| `openid` | 비민감 | 필요 |
| `email` | 비민감. 이 범위 하나만 추가했을 때 민감/제한 범위 목록이 비어 있었다(확인됨, 1회) | 이메일이 필요하면 |
| `profile` | 비민감 | 이름/사진이 필요하면 |
| Gmail, Drive, Calendar 등 서비스 범위 | 민감 또는 제한 | 로그인만 필요하면 요청하지 않는다 |

원칙: **필요한 최소 범위만 요청한다.** 로그인만 하는 앱이 서비스 범위를 요청하면 검증 부담과 사용자 경고가 생긴다.

## 새 프로젝트를 권장하는 이유 (재확인)

동의 화면(앱 이름, 로고, 범위, 지원 이메일, 게시 상태)은 **프로젝트 단위**다. 같은 프로젝트의 다른 클라이언트도 같은 동의 화면을 보여 준다. 기존 서비스가 쓰는 프로젝트에서 앱 이름이나 범위를 바꾸면 기존 서비스의 로그인 화면이 함께 바뀌고, 게시 상태를 바꾸면 기존 사용자의 로그인에 영향이 갈 수 있다. 따라서 앱마다 별도 프로젝트를 쓰는 것이 영향 범위를 가장 작게 만든다.
